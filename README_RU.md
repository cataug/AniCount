# AniCount — полный запуск на HD-видео

Проект: `/home/tahiti/AniCount`. Требуются Linux, Python 3.11–3.12 и свободное место для отдельного окружения. GPU-окружение использует PyTorch 2.6.0 + CUDA 12.4; на занятой GPU автоматический режим выбирает CPU. Для первоначальной установки нужен интернет к PyPI и download.pytorch.org. Модели и датасеты заново не скачиваются.

## Быстрый запуск

Сохранить архив `AniCount_video_full.zip` в `/home/tahiti/AniCount`, распаковать **полностью**, включая папку `anicount_vendor` и файл зависимостей:

```bash
cd /home/tahiti/AniCount
python3 -m zipfile -e AniCount_video_full.zip .
```

Проверить три модели на **одном полном кадре** исходного HD-видео на 1:04.5:

```bash
python3 -u anicount_video.py --at 64.5 --device auto --out outputs/probe_645
```

Первый запуск сам создаёт `/home/tahiti/AniCount/.venv_anicount`, устанавливает зафиксированные зависимости и запускает обработку. Повторные запуски используют это окружение. Отдельная установка без обработки: `python3 -u anicount_video.py --setup`.

Известный исходник выбирается автоматически:

```text
/home/tahiti/AniCount/NG South Sudan 1920x1080 (1).m4v.mp4
```

Двойное расширение учтено. Другой файл задаётся через `--video 'имя файла.mp4'` или абсолютный путь. Присланная запись экрана использовалась для проверки кода; команды выше работают с HD-исходником на сервере.

## Все кадры фрагмента 1:01–1:08 с рамками DMD

```bash
cd /home/tahiti/AniCount
python3 -u anicount_video.py --models dmd --start 61 --end 68 --device auto --out outputs/clip_61_68_dmd
```

`--stride 1` стоит по умолчанию: анализируется каждый кадр. При 30 FPS семисекундный фрагмент содержит 210 кадров. Обработка использует перекрывающиеся плитки 512×512 с перекрытием 160 пикселей; рамки объединяются через NMS. Размер входа DMD по умолчанию 640. Нативный размер из checkpoint — 1280; сравнить его можно параметром `--dmd-size 1280`. На CPU это существенно медленнее, а качество нужно оценивать по изображениям и разметке.

Полный фрагмент **через все три модели**:

```bash
python3 -u anicount_video.py --models dmd owl-c owl-d --start 61 --end 68 --device auto --out outputs/clip_61_68_all
```

Для принудительного CPU: `--device cpu`. Для GPU: `--device cuda:0`. Автоматический режим требует минимум 8 GiB свободной VRAM перед загрузкой; порог настраивается через `--min-free-gb`. CPU/GPU и причина выбора печатаются в логах. Все модели выполняются последовательно, каждая в отдельном процессе. CPU-потоков по умолчанию 4 (`--threads`). OWL-D содержит около 855 млн параметров и на CPU работает значительно медленнее небольших моделей.

Быстрый просмотр каждого третьего кадра: добавить `--stride 3`. Итоговое видео будет иметь FPS, уменьшенный втрое, с сохранением длительности выбранных кадров. `--max-frames 3` позволяет проверить короткий запуск. `--no-video` оставляет таблицы и PNG. `--save-all-frames` дополнительно сохраняет каждый обработанный кадр в PNG.

## Результаты

Для каждой модели создаётся своя папка `dmd`, `owl-c` или `owl-d` внутри указанного `--out`:

| Файл | Содержимое |
| --- | --- |
| `annotated.mp4` | Полный кадр с рамками/точками и подписью снизу; создаётся при обработке интервала, без звука |
| `frames/*.png` | Полные кадры с результатами: первый, последний, примерно раз в секунду и кадр 1:04.5, если он выбран |
| `frames/*_heatmap.npy` | Исходная карта локализации OWL для сохранённых PNG |
| `detections.csv` | Координаты и score каждого обнаружения в пикселях исходного кадра |
| `counts.csv` | Количество обнаружений, исходный номер/время кадра, число плиток и время обработки |
| `metadata.json` | Модель, устройство, параметры, контрольная сумма весов и статус выполнения |
| `run.log` | Живой лог конкретной модели |

В корне запуска находятся `summary.json`, `run_config.json` и `reference_frames/` с выбранными исходными кадрами. Подпись добавляется **под** изображением, поэтому животные не закрываются плашкой. Координаты CSV относятся к исходному изображению без подписи. Нумерация кадров в CSV начинается с нуля.

При наличии FFmpeg с libx264 выход — H.264 MP4. Иначе используется OpenCV MPEG-4. Модель, порог и число обнаружений указаны на видео. При сохранении одного кадра через `--at` создаются PNG и CSV; однокадровый MP4 не создаётся.

## Что предсказывают модели

| Модель | Выход | Визуализация |
| --- | --- | --- |
| DroneMegaDetector / RF-DETR Medium | Настоящие bbox, выбирается класс `animal` (ID 1) | Зелёные рамки |
| OWL-C | Точки локализации | Жёлтые точки |
| OWL-D / DINOv3 ViT-H+/16 | Точки локализации | Жёлтые точки |

Для OWL карты перекрывающихся плиток усредняются в одну карту кадра, затем применяется оригинальный LMDS из опубликованного кода. Это объединяет перекрытия до выделения точек. Координаты вернутся в пиксели исходного кадра с учётом down_ratio=2. Выход OWL не содержит размеров животных, поэтому искусственные bbox из точек не строятся.

Значения `count` — **предсказанные обнаружения на отдельном кадре**. Их нельзя суммировать по времени как число уникальных животных. Трекинг и оценка точности по ручной разметке в этот код не входят. На приложенном примере OWL-C пропускал заметную часть стада. Порог DMD: `--dmd-conf 0.15`; порог точек OWL: `--owl-conf 0.20`; параметры LMDS — `--owl-adapt 0.30 --owl-negative 0.10`.

## Локальные веса

```text
weights/DroneMegaDetector_RFDETRMedium_2026.10.04.pth
weights/OWL-C.pth
weights/OWL-D.pth
```

Веса проверяются по контрольным суммам до загрузки. Для OWL это опубликованные MD5 из Zenodo. Для DMD сохранена SHA-256 официального GitHub asset v1.1, который был скачан и реально запущен при подготовке комплекта. Для OWL используется строгая проверка ключей/размеров `state_dict`. Backbone OWL-D уже входит в `OWL-D.pth`; дополнительный checkpoint Meta не загружается. Во время инференса Hugging Face работает в offline-режиме.

Наборы в `DATA/` для этих запусков не требуются: используются готовые модели. Ошибка доступности Delplanque не блокирует обработку видео.

## Продолжение после остановки

Повторить **ту же команду**, добавив `--resume`, с тем же `--out`:

```bash
python3 -u anicount_video.py --models dmd owl-c owl-d --start 61 --end 68 --device auto --out outputs/clip_61_68_all --resume
```

Законченные модели пропускаются. Для незавершённой модели прошлые результаты переносятся в папку `*.previous_*`, затем эта модель обрабатывает фрагмент заново. Это продолжение по моделям, а не с середины MP4. CSV и PNG сохраняются по мере работы. Параметры, код и исходник при `--resume` должны совпадать; для других параметров используйте новый `--out`. Ошибка одной модели не удаляет результаты остальных. Если GPU-процесс падает из-за OOM в режиме `auto`, контроллер сохраняет его вывод и повторяет ту же модель на CPU.

## Проверки комплекта

На Python 3.12, PyTorch 2.6.0 CPU и точных версиях из `requirements_inference.lock`:

- Реальные официальные веса DMD загружены и запущены на присланном кадре 1464×836: 290 bbox при входе 640 и 218 bbox при 1280, порог 0.15. Это обнаружения, не ручной эталон. Пример с 640 есть в `example_results/dmd_example_640.png`.
- Реальный checkpoint OWL-C проверен по MD5, строго загружен и запущен: на том же кадре 84 точки при пороге 0.20.
- Проверено декодирование записи экрана, плитки, NMS, CSV/PNG, обработка нескольких кадров и создание H.264 MP4 с правильным числом кадров/FPS.
- Проверен численный CPU-проход архитектуры OWL-D / OWLD_H с тестовыми параметрами и входом 64×64, включая распаковку tuple-выхода, stitching и выделение пиков. Реальный 3.5 GB checkpoint OWL-D в этой среде не запускался.
- GPU и серверный HD-исходник в этой среде недоступны. Эти запуски выполняются на вашем сервере.
